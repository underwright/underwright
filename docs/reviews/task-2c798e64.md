## Findings

### F1 — Medium: `PgStore.leaseNodeJob` capacity check is a TOCTOU; concurrent pollers can over-lease (`src/pstore.ts`)

The gate reads `running` rows `FOR UPDATE` and then leases a queued row in the
same transaction:

```ts
const running = (await s.nodeQuery(
  "SELECT * FROM jobs WHERE type='node' AND target_node_id=? AND status='running' AND lease_expires>now() FOR UPDATE", ...));
...
const queued = running.length < maxConcurrency ? (await s.nodeQuery(
  "SELECT * FROM jobs ... status='queued' ORDER BY created_at,id LIMIT 1 FOR UPDATE SKIP LOCKED", ...))[0] : undefined;
```

Under READ COMMITTED, `SELECT ... FOR UPDATE` locks only rows that matched the
predicate at scan time. A row flipped `queued→running` by a *concurrently
committing* lease is a phantom for this statement: two slot polls can both
observe `running.length = max-1`, each lease one queued job, and both commit —
leaving `max+1` jobs running. The feature's entire premise is that attested
`max_concurrency` bounds parallelism; this window is widened by the very thing
the PR adds (N concurrent pollers from the same node).

`SqliteStore` is not affected — `nodeTransaction` serializes the whole closure
(single writer), so the count and the lease are atomic.

Suggested fix: take a per-node serialization point before the count — e.g.
`SELECT id FROM nodes WHERE id=? FOR UPDATE` inside the transaction (the node
row is already fetched unlocked one line earlier), or
`pg_advisory_xact_lock(hashtext(node_id))`. Either makes the
read-count-then-lease atomic per node without touching semantics.

### F2 — Low: old-session `running` jobs consume capacity but can never be re-delivered or finished

`held` re-delivery requires `session_id === sessionId`, and
`authenticateNode(token, sessionId)` rejects any session that isn't the node's
current `session_epoch`. After daemon restart or the gh-110 re-session path,
every job left `running` under the dead session (a) counts toward
`running.length` and (b) is unreachable: it can't be re-delivered, renewed, or
finished — it burns to `lease_expires` (≤ `NODE_LEASE_SECONDS`=60s, plus
sweep/grace) before a slot frees. Pre-existing for one slot; gh-91 multiplies
the stall to N slots on every re-auth. Cheap follow-up: in
`startNodeSession`, mark same-node `running` jobs from superseded sessions
`outcome_unknown` at session issuance — the epoch flip already proves they're
orphaned.

### F3 — Low: `held` re-delivery is now subordinate to new leases; a lost poll response can strand a running job

Pre-change ordering was held → busy → lease. Now `held` is consulted only when
no queued job was leased (`!queued → held ? ... : 204`). If a poll response is
lost client-side (server committed the lease, client timed out) while the
queue is non-empty, the abandoned `running` job is never re-delivered — every
subsequent poll leases fresh work — until its lease expires and the sweeper
marks it `outcome_unknown`, even though the journal-resume path exists to
recover exactly this case. Rare and arguably the right throughput trade-off,
but it's a semantic change worth an explicit note; if unintended, return
non-excluded `held` before leasing when `exclude` provably doesn't cover a
same-session running job.

### F4 — Low: server-side lease paths lack direct tests; daemon dedup path untested

The two new tests exercise 2-slot parallelism and clamping end-to-end through
a real `SqliteStore` + HTTP — good coverage of the happy path. Not covered:

- capacity refusal: third concurrent poll on a `max_concurrency=2` node → 204;
- `held_job_ids` exclusion preventing re-delivery of a held job;
- `held` fallback re-delivering a same-session running job (the
  `publicNodeJob(held)` branch in both stores);
- the daemon's `activeJobs.has(job.id) → continue` duplicate-delivery path.

The issue AC also lists "worker crash kills only its job" — structurally true
(jobs are already `execFile` children; `AttemptJournal` is keyed per
job+attempt so parallel `journal.write` calls can't collide), but no test
kills a child mid-flight under a multi-slot daemon.

### F5 — Minor

- `docs/node-executors.md` says the server "prefers nodes with free slots when
  routing" — verified true: `selectNode` ranks `current_slots < max_concurrency`
  (`src/node-protocol.ts:259-285`). Good.
- Merged commit sent singular `active_job_id` in heartbeats (first element of
  the set, arbitrary under multi-slot); later commits already send
  `active_job_ids`. Superseded — noting for completeness.
- Daemon: `if (activeJobs.has(job.id)) continue` after duplicate delivery
  costs one extra poll round-trip, then the refreshed `held_job_ids` yields
  a clean 204 — bounded, correct. `has`+`add` is synchronous so the Set check
  is atomic on the event loop; no client-side double-execution path found.
  `finally { if (held) activeJobs.delete(...) }` is correctly guarded.
- The node-state gate moved ahead of the `held`/busy checks; a node flipped
  non-approved now gets bare `nodeError()` (401) where it previously could
  still receive its held job. Reasonable hardening; the 401 status also reads
  as "session dead" to the daemon (it will re-auth and fail the same way), so
  the status code is slightly misleading but harmless.
- `src/init.ts` bundles unrelated AGENTS-rule additions ("Where work comes
  from", "Wrong model for the job?", "Git hygiene") and `test/node-queue.test.ts`
  carries an unrelated test repair (`provision` kind for retry semantics).
  Harmless scope creep, worth noting for future PRs.
- Each long-poll retry re-runs `leaseNodeJob`; on Postgres that re-locks every
  running row `FOR UPDATE` ~every 50ms per slot, so N-slot fleets serialize
  and can convoy on those row locks. Later throttle commits (`f313d2c`,
  `c78edad`) already reduced sweep/write pressure; the row-lock pattern
  remains worth watching.
